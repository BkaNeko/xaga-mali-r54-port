# 950 MHz 的前因后果

一句话：**950 MHz 一直是固件里现成的一档，只是固件的选档循环把它永久排除了。**
改 5 个字节就能用上，但 AP 侧任何接口都碰不到它。

---

## 1. 固件里本来就有的表

GPUEB 是 MT6895 上的 RISC-V 协处理器，GPU 的频率 / 电压 / 电源域由它独占控制。
它的 GPU OPP 表在固件偏移 `0x15d60`，6 项，每项 24 字节
（与 AP 侧 `struct gpufreq_opp_info` 布局一致）：

| idx | freq (kHz) | volt | vsram | posdiv | 说明 |
|---|---|---|---|---|---|
| 0 | **950000** | 78750 | 78750 | 2 | **固件永远不选这一档** |
| 1 | 880000 | 78750 | 75000 | 2 | 实际能到的最高档 |
| 2 | 800000 | 72500 | 75000 | 2 | |
| 3 | 610000 | 65000 | 75000 | 2 | |
| 4 | 430000 | 60000 | 75000 | 2 | |
| 5 | 350000 | 57500 | 75000 | 3 | |

电压单位是 **0.1 mV**，驱动提交时乘 10 转成 µV：

```c
regulator_set_voltage(g_pmic->reg_dvfsrc, volt_new * 10, INT_MAX);
```

所以 950 MHz 用 **78750 × 10 = 787 500 µV = 787.5 mV**。

**注意：950 和原厂 880 是同一个电压（787.5 mV）。**
也就是说 950 这一档不需要额外加压，是固件原厂给出的组合。

## 2. 为什么用不上：循环边界写的是 `i > 0`

固件里的选档逻辑等价于 AP 侧这段源码（`gpufreq_mt6895.c`，
`__gpufreq_get_hw_constraint_fgpu()`）：

```c
/*
 * Fstack <= 800MHz: find Fgpu >= Fstack*1.1
 * Fstack > 800Mhz: Fgpu = 880MHz (OPP[0])      <-- 880 曾经就是 index 0
 */
for (i = min_oppidx; i > 0; i--) {              <-- 边界没跟着改
    target_freq = working_table[i].freq * GPUFREQ_BASE_COEF;
    if (target_freq >= fstack * GPUFREQ_CONSTRAINT_COEF)
        break;
}
```

这段代码写的时候表只有 **5 档**，880 MHz 在 index 0。
后来 950 插到 index 0，**循环边界 `i > 0` 没跟着改，index 0 被永久排除**。
注释里 `"Fgpu = 880MHz (OPP[0])"` 就是那时代码的活化石。

### 数学佐证

STACK 域最高 852 MHz，按 MTK 自己的约束 `Fgpu >= Fstack × 1.1`：

```
852 × 1.1 = 937.2 MHz
```

固件给的是 880 MHz —— **连它自己的约束都没满足**。
所以 880 不是「最优选择」，是「被截断后的错误结果」。
950 MHz 恰好是唯一能满足该约束的档位。

## 3. AP 侧为什么绕不过去

三条路都试过，全部堵死，都有实测依据。

### 3.1 `gpufreq_commit(TARGET_GPU, idx)` 无效

`tools/gtprobe.c` 是专为此写的内核探针模块，直接调用导出的 `gpufreq_commit()`：

```
commit(target=TARGET_GPU, idx=0) ret=0 -> cur_idx=1 freq=880000
commit(target=TARGET_GPU, idx=1) ret=0 -> freq 不变
commit(target=TARGET_GPU, idx=2..5) ret=0 -> freq 不变
```

**返回 0 只代表 IPI 消息送达。固件只认真 `TARGET_STACK`。**

### 3.2 所有用户空间写接口都落在 STACK 域

`gpufreq_validate_target()` 在 dual-buck 下重映射：

```c
if (*target == TARGET_DEFAULT) {
    if (g_dual_buck) *target = TARGET_STACK;
    else             *target = TARGET_GPU;
}
```

而 `/proc/gpufreqv2/` 下**所有**写接口（`fix_target_opp_index`、
`fix_custom_freq_volt`、`set_limit`、`switch_limit`）用的都是 `TARGET_DEFAULT`。
所以写 950000 会被送到 STACK 域，直接超出范围：

```
[GPU/FREQ][ERROR]@gpufreq_fix_custom_freq_volt: fail to fix STACK freq: 950000, volt: 78750 (-1)
```

### 3.3 EB 模式下 AP 侧策略是空壳

```c
static struct gpuppm_platform_fp platform_eb_fp = {};   /* 全空 */
```

一行都不执行，全部交给固件。

## 4. 修法：改固件表的 entry[1]

把「固件够得着的最高档」改成 950：

```
0x15d78: 80 6d 0d 00  ->  f0 7e 0e 00    (880000 -> 950000)
0x15d80: f8 24 00 00  ->  9e 33 00 00    (75000  -> 78750)
```

共 **5 个字节**，文件大小不变。vsram 同步成库存 950 档的 78750。

### 补齐到分区大小用 0x00，不是 0xFF

OTA payload 里的 gpueb 只有 128 KiB，而分区是 1 MiB。
原厂镜像在 `0x20000` 之后**全是 0x00**：

```python
padded = patched + b"\x00" * (1048576 - len(patched))
```

验证标准：与原厂 1 MiB 镜像**只差这 5 个字节**（md5 `bd0476b4…`）。
早期用 0xFF 补齐过，虽然也能跑，但和原厂不一致。

```bash
python3 tools/gpueb_patch.py gpueb.img gpueb_950.img --pad-to 1048576
```

### 刷到当前槽

```bash
fastboot getvar current-slot            # 先确认！
fastboot flash gpueb_b gpueb_950.img    # 当前是 b 就刷 gpueb_b
```

槽位会变：开机失败时 Android 的 boot control 会自动切槽，
刷错槽的表现就是「刷了但没生效」。这一步踩过。

## 5. 验证

```bash
# 固件表：[01] 应该变成 950000
su -c 'sed -n 1,2p /proc/gpufreqv2/gpu_signed_opp_table'

# 硬件频率计（不是软件上报值）
su -c 'cd /data/local/tmp && (for i in $(seq 1 30); do ./glbench 1280 720 3000 >/dev/null 2>&1; done) &'
sleep 4
su -c 'grep -E "GPU-OPP|GPU-REALOPP" /proc/gpufreqv2/gpufreq_status'
```

实测：

```
[GPU-OPP]     Index: 1, Freq: 950000
[GPU-REALOPP] FmeterFreq: 950015        <- 硬件读数 950 MHz
```

持续满载 60 秒：无 fault、无复位，温度 46–54 °C。

## 6. 连带修的三个调度问题

固件补丁生效后，实测**只有 950 和 350 两档，中间档全消失**。
三个原因叠加，都在 AP 侧调度里：

### 6.1 STACK 索引错配

提交走 `TARGET_DEFAULT` → 被重映射成 `TARGET_STACK`。
而策略直接把 **GPU 域索引**（0..5）当 STACK 索引传出去，
STACK 表 40 档，索引 0..5 = 852/845/837/830/822/815 MHz，**全在最高端**。
所以不管策略要哪一档，固件推导出的 GPU 都是最高档。

修法：`mtk_stack_idx_for_gpu()` 按频率在 STACK 表里找最接近的档位。

### 6.2 档位重复

补丁后 index 0 和 index 1 都是 950 MHz，策略表里出现两个相同档位，
浪费一个台阶且阈值对不齐。修法：建表时跳过相邻重复频率。

### 6.3 升降档时间严重不对称

```c
升档：2 次 tick = 40 ms
降档：hold 10 次 + 50 次 tick = 1.2 s
```

升上去就几乎降不下来；再加上阈值 `loading >= 70` 在满载时长期成立，
策略直接钉在最高档 —— 日志里 `4->0` 刷屏、`stack_idx=7` 只出现一次。

修法：

```c
mtk_hold_ticks = 5;              /* 200ms -> 100ms */
if (++mtk_down_ticks < 8)        /* 50 次(1s) -> 8 次(160ms) */

/* 阈值上移，最高档只留给真正饱和的负载 */
loading >= 90 → 最高档      (原 70)
loading >= 70 → 次高档
loading >= 45 → 中档
loading >= 20 → 次低档
其余         → 最低档
```

修完四档都在用：

```
stack_idx=0    6 次   → 950 MHz
stack_idx=7   12 次   → 800 MHz
stack_idx=14  31 次   → 710 MHz
stack_idx=24  21 次   → 586 MHz
```

## 7. 收益：频率 +8%，跑分 +1.5%

| 状态 | 3DMark Wild Life |
|---|---|
| 原厂 r32（880 上限）| ~6000 |
| r54 + GED + gpueb，880 | 5730 |
| r54 + 全套 + 950 | **5814** |

核心频率 +8%（880→950），跑分只 +1.5%。
差掉的 6.5% 说明这个负载下瓶颈不在核心频率 —— 填充率、内存带宽或散热先到顶。

**记在这里是为了不高估固件补丁的收益**：它确实让硬件跑到 950 MHz
（`FmeterFreq` 硬件实测），但实际收益远小于频率提升幅度。

## 8. 顺带确认的两件事

**固件无签名校验**：固件头只有 magic（`0x88168858`）、size、名字
（`tinysys-gpueb-RV33_A`）和第二个 magic（`0x89168958`），
没有任何 hash / 签名字段；payload 约 96 KiB，熵 0.972（未加密未压缩）。
改完 bootloader 正常加载，说明这条路上没有校验。

**双槽冗余**：`gpueb_a` 和 `gpueb_b` 出厂内容完全相同
（md5 `07dd0afd…`），可以互为备份、随时回滚。
